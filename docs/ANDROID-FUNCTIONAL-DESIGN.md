## 0. 假设与范围（先摆出来，错了就改）

| # | 假设 | 影响 |
| --- | --- | --- |
| A1 | 单人使用，不做账号体系 | 无登录/权限/多租户，凭据只有 GitHub PAT |

## 1. 现状盘点（Android）

| 能力 | 状态 | 缺口 |
| --- | --- | --- |
| 新建条目 | ❌ | 原样字段改错后无路可走 |
| 删除 / 恢复 | ❌ | 内核有 `Tombstone`，UI 全无 |
| 撤销 / 历史 | ❌ | 事件日志齐全，缺读取与回滚接口 |

| 错题本 | ❌ | 无「连续答错」聚合 |

| 搜索 | ❌ | 只有"线索反查"，不能按名字/拼音找 |
| 凭据安全 | 🟡 | 明文 `shared_prefs` + `sync.json` |

## 3. 功能清单

编号规则：`F-<域>-<序号>`。每条都给「入口 / 前置 / 结果 / 失败路径 / 验收」。

### 3.1 录（Capture）

#### F-CAP-01 新建条目
- **入口**：矩阵页底部「＋ 新建」；某条目的「复制为新」。
- **前置**：已装载 schema。
- **流程**：选实体类型（单领域时自动）→ 空表单（17 字段，`immutable` 为空可填、`required` 标星）→ 保存。
- **结果**：`createEntity` 写一条 `UpsertEntity`，`rev = 1`（新 id），返回后跳转到该条目明细。
- **失败**：
  - 主键为空 → 前端拦截（`required`）；
  - 主键重复 → 提示「已存在《麻黄》，去编辑 / 仍要新建」；
  - `immutable` 字段留空 → 允许（草稿态），但明细页标「原样字段缺失」。
- **复制为新**：把现有条目全部字段预填，主键清空并加后缀建议（`麻黄（我的修订）`），保存后 `supersedes = 原 id`。
- **验收**：新建一条 → 矩阵出现 → 反查可命中 → 同步后另一设备可见。

#### F-CAP-02 原样字段纠错（新建并替代）
- **入口**：编辑面板里原样字段旁的「新建修订版」。
- **流程**：以当前条目为模板 → 主键预填「原名（修订 yyyy-MM-dd）」→ 原样字段可改（因为是新条目）→ 保存 `supersedes`。
- **结果**：新条目 `supersedes=旧 id`；旧条目自动打「已被替代」标记，矩阵默认隐藏，可在「显示被替代」开关下看到。
- **验收**：原条目从旧 id 复制 → 改用量 → 保存 → 矩阵只剩新条目；反查只命中新条目。

#### F-CAP-03 粘贴解析（多行 → 字段）
- **入口**：新建面板「从文本粘贴」。
- **规则**：按行解析 `标签：值`（中英文冒号都认）；标签匹配字段 `label` 或 `key`；未匹配行整体进「特点锚」或提示未识别；`|` / `、` 分隔的按 `tags` 处理。
- **结果**：填入表单（不直接保存），高亮识别失败的字段。
- **验收**：粘贴 17 行教材文本 → ≥14 个字段自动填对；剩余字段手动补。

#### F-CAP-04 拍照 OCR → 草稿
- **入口**：新建面板「拍照识别」。
- **流程**：拍照 → 本地 OCR（ML Kit）→ 文本进 F-CAP-03 解析 → 生成草稿（可编辑）→ 保存。
- **边界**：识别结果只进草稿，**绝不直接入库**；一页多味药时按「主键行」切分成多条草稿。
- **验收**：拍一页教材 → 至少生成 1 条可保存的草稿，且原样字段标注「待核对」。

#### F-CAP-05 删除 / 回收站 / 恢复
- **入口**：明细页「删除」；数据页「回收站」。
- **规则**：删除 = `Tombstone`（保留 30 天）；回收站列出 `deleted=true` 的条目与删除时间；恢复 = 写回 `UpsertEntity`（`deleted=false`，`rev+1`）。
- **边界**：已被上游移除但本地改过的条目，删除时提示「公共库已移除，本地仍保留」。
- **验收**：删除 → 矩阵消失 → 回收站可见 → 恢复 → 矩阵回来且反查恢复。

### 3.2 学（Learn）

#### F-LEARN-01 今日队列
- **入口**：复习页首屏显示「今日 N 张（到期 a / 新 b）」。
- **配额**（可配，默认）：到期 50 / 新 10。
- **取卡顺序**：到期卡按 `due` 升序（越逾期越前）→ 新卡按药群顺序 → 会话内不重复。
- **边界**：
  - 到期为 0 且有新卡 → 只出新卡；
  - 两者都 0 → 显示「今日已完成，明日 X 张」；
  - 跨天（本地 0 点）重新计算。
- **接口**：`quizQueue(newLimit, dueLimit)` → `{due, new, items:[cardId]}`。
- **验收**：当天多次进入，题集不变；第二天到期数变化。

#### F-LEARN-02 自动评分建议
- **输入**：判分结果（`correct` / `score`）、本题耗时。
- **规则**：

| 判分 | 耗时 | 建议 grade |
| --- | --- | --- |
| 错误 | — | 1 重来 |
| 正确 | > 15s | 2 困难 |
| 正确 | 5–15s | 3 良好 |
| 正确 | < 5s | 4 简单 |

- **呈现**：评分按钮默认高亮建议项，用户可改（4 档全给）。
- **接口**：`suggestGrade(cardId, correct, elapsedMs)` → `{grade, reason}`（纯函数，桌面端复用）。
- **验收**：答对 3 秒内 → 默认「简单」；答错 → 默认「重来」。

#### F-LEARN-03 会话内重试
- **规则**：答错的卡在本次会话内 5 分钟后重新入队（内存队列，不写事件）；同一卡本次最多重试 1 次，避免死循环。
- **验收**：故意答错 → 该卡在 5 分钟后再次出现 → 答对后不再出现。

#### F-LEARN-04 错题本（薄弱集合）
- **规则**：连续答错 ≥2 次（按 card 粒度，取最近 30 天事件）→ 进「薄弱」；答对 2 次连续 → 移出。
- **入口**：复习页「薄弱 N 张」独立开始。
- **接口**：`weakCards(limit)` → `[{cardId, entityName, direction, lapses}]`。
- **验收**：构造 2 次错答 → 薄弱出现该卡；连续答对 2 次 → 消失。

#### F-LEARN-05 掌握度派生
- **规则**（复习事件后重算，写回 `mastery`）：

| 条件 | 值 |
| --- | --- |
| `lapses >= 2` 或 `stability < 1` | 生疏 |
| `1 <= stability < 7` | 熟悉 |
| `stability >= 7` 且最近一次 grade ≥ 3 | 熟练 |

- **手工覆盖**：用户手填后写 `mastery_override_at`；30 天内派生不覆盖；到期自动恢复派生。
- **验收**：连续复习 3 次「良好」→ 矩阵里该药从「生疏」变「熟悉」→ 考前差异视图不再列出。

### 3.3 库（Library）

#### F-LIB-01 明细页
- **内容**：主键 + 17 字段（原样字段带「原样」标记）+ 掌握度 + 最近复习时间 + 「历史」入口。
- **操作**：编辑、复制为新、删除、查看历史。
- **验收**：从矩阵/搜索/反查任一入口进入，看到同一份数据。

#### F-LIB-02 搜索
- **能力**：按主键、同义词、功效、应用做子串/前缀匹配；结果按「主键命中 > 同义词 > 反向索引」排序。
- **接口**：`search(query, limit)` → `[{id, name, group, snippet, score}]`。
- **边界**：空串不查；单字查询允许（中文单字有意义）。
- **验收**：输入「麻黄」命中；输入「发汗」按功效命中多味。

#### F-LIB-03 历史时间线
- **内容**：该条目字段级变更列表（时间、设备、字段、从→到）。
- **接口**：`history(entityId)` → `[{rev, ts, device, changes:[{key, before, after}]}]`。
- **边界**：只读；跨设备事件按 `ts` 排序；`rev` 不连续是正常的（其他条目占用了 rev）。
- **验收**：改一个字段 → 历史出现一条，`before/after` 正确。

#### F-LIB-04 撤销
- **范围**：只支持「撤销最近一次编辑」，且仅当该条目在当前会话内被改过。
- **实现**：读取该次变更的 `before` 值，写回一条新 `UpsertEntity`（**rev 递增，不是回退 rev**）。
- **边界**：撤销后不可重做（v1）；跨设备不改同一条。
- **验收**：改字段 → 撤销 → 值回原样，且历史里出现两条记录（改 + 撤销）。

### 3.4 数据（Data）

#### F-DATA-01 同步（已有，补强）
- 补：同步前检查「有未提交裁决」→ 拒绝并提示；同步中显示阶段（fetch/push/commit）；失败给出可操作提示（412 自愈已内置）。
- 补：`bytes_up/down`、耗时、冲突数在回执里保留（已有）。

#### F-DATA-02 公共库拉取（已有）
- 补：`unchanged` 与非 `unchanged` 文案区分（已修）；拉取前展示「新增/自动合并/冲突」预估。

#### F-DATA-03 凭据安全
- **目标**：`sync.json` 不含明文 token。
- **方案**：Kotlin 用 Android Keystore（EncryptedSharedPreferences）保存 token；`configureSync` 时注入内存；Rust 落盘时把 token 写成占位符 `"${CREDENTIAL:github-token}"`；冷启动由 Kotlin 读 Keystore 后注入。
- **接口**：`configureSync(configJson)` 增加约定字段 `credential_ref`；`setCredential(name, value)`（内存）。
- **验收**：`run-as cat sync.json` 看不到 `ghp_`；杀进程重启后同步仍可用。

#### F-DATA-04 导入导出（已有）
- 补：导入前差异预览（新增/更新/冲突计数），可取消。
- 补：导入结果里列出「被跳过」的原因。

## 4. 状态机

### 4.1 复习会话

```
Idle → Loading(quizQueue) → Answering(card, startedAt)
  → Judged(score, suggestedGrade) → Rated(grade) → [next card | RetryQueue | Done]
  ↘ 退出（保留已写事件，未答卡不记）
```
- 事件写入点：`Rated` 时写 `ReviewEvent`（唯一写入点，撤销/重放都靠它）。
- 中断：进程被杀 → 已评分的保留，未评分的丢弃。

### 4.2 编辑会话

```
View → Editing(dirty?) → Saving → Saved(newRev) | Failed(原因)
Saved → 可撤销窗口（本会话）
```
- `dirty=false` 时保存按钮禁用（已有）。
- 保存失败（immutable / 类型错 / 未知字段）→ 停留在 Editing，错误点名字段。

### 4.3 同步会话

```
Idle → Fetch(public/private) → Push(events) → Commit → Done(receipt)
                    ↘ Conflict(412 已自愈) ↘ Error(带 http 状态与响应体)
```

## 5. FFI 契约变更（本轮要加的）

所有方法沿用现有约定：入参 JSON 字符串，返回 JSON 字符串，错误 `{"error":"..."}`。

| 方法 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `createEntity` | `kind`, `fieldsJson` | `{ok,id,rev}` | 新 id 由主键稳定生成；重名返回 `{error, existing_id}` |
| `deleteEntity` | `entityId` | `{ok,id,deleted_at}` | 写墓碑 |
| `restoreEntity` | `entityId` | `{ok,id,rev}` | 取消墓碑 |
| `listDeleted` | — | `{items:[{id,name,deleted_at}]}` | 回收站 |
| `history` | `entityId` | `{items:[{rev,ts,device,changes}]}` | 从事件日志推导 |
| `undoEdit` | `entityId` | `{ok,rev,restored:[keys]}` | 仅本会话最近一次 |
| `quizQueue` | `newLimit`, `dueLimit` | `{due,new,items}` | 每日配额 |
| `suggestGrade` | `cardId`, `correct`, `elapsedMs` | `{grade,reason}` | 纯函数 |
| `weakCards` | `limit` | `{items:[...]}` | 错题本 |
| `search` | `query`, `limit` | `{items:[...]}` | 全库检索 |
| `parseFields` | `text` | `{fields, unmatched}` | 粘贴解析（Rust 侧做，桌面复用） |
| `setCredential` | `name`, `value` | `{ok}` | 内存凭据，不落盘 |

**实现状态**：`createEntity` / `deleteEntity` / `restoreEntity` / `listDeleted` / `entityHistory` / `undoEdit` / `entityTemplate`（新建表单定义）**已实现并有单测**（A1）；`quizQueue` / `suggestGrade` / `weakCards` / `search` / `parseFields` / `setCredential` 待 A2/A4。`state()` 新增 `kind` 与 `recycle` 两个字段。

**兼容性**：只增不改。`view()` 已加 `_id`；`entityDetail` / `editEntity` 保持。

## 9. 桌面端方案评估（结论：Compose Multiplatform Desktop）

| 方案 | 代码复用 | 代价 | 风险 |
| --- | --- | --- | --- |
| **A. Compose Desktop（JVM）** | **Kotlin UI ≈ 80–90%，Rust 内核 100%** | 需把 UI 里 Android 专有 API 抽成接口（OCR/权限/文件选择） | JNI dll 打包、窗口与文件对话框差异、包体 ~80MB |
| B. 网页 + 本地 Rust 服务 | 内核 100%，UI 0 | 双份 UI、双份交互逻辑 | 两套代码长期漂移 |
| C. Tauri（WebView + Rust） | 内核 100%，UI 0 | 同 B，且多一层壳 | 同上 |
| D. egui / iced（纯 Rust） | 内核 100%，UI 0 | 表格/输入控件要重写 | 中文输入法与表格体验差 |

**选 A**，理由：
1. 你要求「尽可能复用手机端代码」——A 是唯一复用 UI 层的方案；
2. 现有 Kotlin 侧已经做了 `Api` 门面 + 纯函数式展示层，抽 `expect/actual` 成本可控；
3. Rust 内核通过 uniffi 生成 JVM 绑定（`mneme_ffi.dll` / `.so`），与服务端方案共享同一套业务逻辑，不需要维护第二份。

**为此现在就要遵守的约束**（否则以后拆不动）：
- 业务状态与 UI 分离：`Api` 之上再加一层 `Store/Reducer`（纯 Kotlin，无 Android import）；
- Android 专有能力（OCR、相机、Keystore、文件选择）走接口注入，不在 UI 里直接调；
- 表单校验、评分建议、字段解析这类逻辑全部下沉到 Rust（桌面端零重写）。

## 10. 实施顺序（每步可独立验收）

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **A1 数据完整性** | 新建/复制为新、删除/回收站/恢复、历史、撤销、`notes`/`supersedes` 字段 | §8 第 1–4 项 |
| **A2 复习闭环** | 每日队列、自动评分、会话内重试、错题本、掌握度派生 | §8 第 5–8 项 |
| **A3 录入效率** | 粘贴解析、OCR 草稿、重复检测、导入差异预览 | §8 第 1 项（≤2 分钟） |
| **A4 安全与检索** | Keystore 凭据、搜索、场景脚本化 | §8 第 9、11、12 项 |
| **A5 桌面端** | Compose Desktop 骨架 + 复用 A1–A4 的业务层 | 桌面能完成 §8 第 1–12 项 |

**先做 A1**：它把「能改不能建/不能删/不能撤」这条断链接上，是当前最影响日常使用的一块，也最容易被真机验证。
