# 桌面端基线：冷启动 / 写入 / 检索的实测数据

> 测量日期：2026-11-10　命令：`mneme bench-startup`
> 结论先行：**瓶颈完全不在 UI 框架，而在 store 派生层。**
> 第一轮测量后按 §5 的清单做了修复，**2000 味药冷启动 3091 → 199 ms（15×）**，
> 单条编辑 294 → 15 ms（19×）。修复后的数据见 §3b。

## 1. 环境（性能只认同环境对照，跨机器不可相减）

| 项 | 值 |
| --- | --- |
| CPU | AMD Ryzen AI 9 H 365（Zen5，8C16T） |
| 磁盘 | HS-SSD-A4000 1024G（NVMe） |
| 系统 | Windows 11 企业版 LTSC |
| 工具链 | rustc 1.98.1 / cargo 1.98.1，`--release`（LTO=fat、codegen-units=1、strip） |
| 领域包 | `domains/materia-medica.toml`（21 字段） |

## 2. 方法

```bash
cargo build --release -p mneme-cli
./target/release/mneme.exe bench-startup --entities 500  --rounds 9
./target/release/mneme.exe bench-startup --entities 2000 --rounds 5
```

- 先用一次批量 `mutate` 造库（等价于导入一整份数据），再反复 `Store::open_timed` 取中位数与 p95；
- `open` 的四段（快照 / 重放 / 派生 / 刷镜像）由新增的 `OpenTimings` 计时，与 `open` 行为完全一致；
- 实体按 schema 真实字段形状填满：长文本字段（应用/笔记/鉴别）80 字、其余 20 字、tags 3~5 个；
- **术语多样性按真实教材建模**：720 个不同术语，平均每个词 2~6 味药在用。
  这一点很关键——第一版语料只用了 12 个词循环，倒排 posting 被放大几十倍，
  卡片生成里的歧义判定被拖慢，测出来是假瓶颈（那组数据已废弃，见 §6）。

| 事件日志 | 0.8 MB | 3.0 MB | 3.8× |
| 库目录合计 | 16.2 MB | 70.8 MB | 4.4× |
| **冷启动 wall（中位）** | **204 ms** | **3091 ms** | **15×** |
| ├ 快照读取 | 0.1 ms | 0.1 ms | — |
| ├ 重放日志 | 5 ms | 32 ms | 6× |

| └ 全量重刷 SQLite | 76 ms | 577 ms | 7.6× |
| 首屏整表投影 | 2.2 ms | 9.6 ms | 4× |
| 检索（一次） | 4.3–5.2 ms | 32 ms | 7× |

| 单条编辑（首次，冷） | 287–373 ms | 3210–3299 ms | — |

拆解归因：

| 项 | 500 味 | 2000 味 | 说明 |
| --- | --- | --- | --- |

## 3c. 卡片懒加载之后

`Store::open` 不再装载卡片：矩阵页只要一个数字，而卡片要 34 k 张、12 MB、80 ms。
数字来自 SQLite 镜像里的 `meta.cards_n` 水位；真正要卡片内容的入口（复习 / 判分 /
错题本 / 导出）调 `ensure_cards()` 装一次，之后常驻。

| 指标 | 500 味 | 2000 味 |
| --- | --- | --- |
| **冷启动 wall（中位）** | **22.4 ms** | **121.6 ms** |
| 首次装卡（进复习/导出时一次性） | 11.9 ms | 78.8 ms |
| 单条编辑（稳态） | 4.4–7.0 ms | 15.1–18.3 ms |
| 检索 | 1.29 ms | 10.4 ms |

冷启动三段（2000 味）：重放 32 + 索引 47 + 镜像 34，卡片 0。
到这里「打开窗口就能看矩阵」的成本已经和「卡片数量」解耦了。

## 4. 三个结论

1. **UI 框架不是瓶颈。** 冷启动 3 秒时，其中 3.0 秒在 Rust 侧；壳换成 egui 也只能省下
   wry/Compose 那 100–300 ms。修完之后（500 味 34 ms / 2000 味 199 ms），壳的固定开销
   反而成了大头——这正是「先修内核再选壳」的理由：顺序反了会花时间优化错的东西。
2. **卡片生成是首要问题，且超线性。** 13 张卡 154 µs→1162 µs（数据 ×4，单条成本 ×6）。
   机制已定位到：**歧义候选数随库增长**——500 味时这条药没有任何同线索药（候选 0 个），
   2000 味时它的 13 张卡合计带出 24 个候选，于是每张卡都要拼候选名单、
   把「具有『X』的是？」升级成「列举并说差异」的长题面与长答案。
   也就是说：库越大，「有歧义」的线索越多，每张卡越贵 —— 双重放大。
   2000 味 2.6 秒，5000 味会到 10 秒以上。
3. **每次 `open` 都全量重刷 SQLite，是第二大项（76→577 ms），而且纯属浪费**：
   真相源是事件日志，镜像只在缺失/落后时才需要重建；现在每次启动 DELETE+INSERT 全表，
   还让 WAL 涨到与主库等大（33.9 MB WAL / 3 MB 事件）。

顺带发现（不在关键路径，但都该修）：

- **单条编辑 60–294 ms**：每次写都 `cards.clone()` 克隆全部卡片、再全量重建倒排索引；
  桌面端「边打字边保存」会被这一下卡住。
- **检索 4.3→32 ms**：线性扫描本身没问题，但每次查询都对每条实体的每个字段重新
  `normalize_mapped`（分配 String）。该缓存。
- **从不自动生成快照**：`snapshots/` 恒为 0，所以每次启动都从最早的事件重放；
  重放目前只要 32 ms，但事件会随时间线性增长，最终必须靠快照截断。
- **WAL 从不 checkpoint**：目录 70.8 MB 里 33.9 MB 是 `index.sqlite-wal`。

## 5. 修复清单（已全部落地）

| 修复 | 做法 | 实测效果（2000 味） |
| --- | --- | --- |
| 卡片持久化 | 按实体分块写 `cards.bin`（紧凑二进制，非 JSON）；块指纹=自身 rev + 领域包 + 分组版本 + **同线索词 posting 的成员集合** | 派生 2466 → 44 ms（命中缓存时只校验指纹） |
| 卡片按实体分块 | `Memory.cards: BTreeMap<entity_id, Vec<Card>>` + `card_owner`，替换一条的卡是 O(log n) | 写入不再克隆 3.4 万张卡 |
| 索引槽位化增量 | `ids: Vec<Option<String>>` + `by_id` + 空闲槽；`upsert` 只摘自己那条 posting | 写入不再全量重建索引（22 ms → 0.3 ms） |
| SQLite 按水位补差异 | 镜像存 `(rev, 十六进制 fast_fp, deleted)`，启动比对只写脏行；`meta.events_n` 记录事件水位 | 577 → 33 ms |
| 廉价实体指纹 | `Entity::fast_fp()`（FNV-1a，不分配 `display()`）只给镜像用；合并/同步仍用 sha256 版 | 镜像比对 30 → 6 ms |
| 检索无分配匹配 | `NormMatcher`（KMP 前缀表每词建一次）+ `keep_char` 流式比较，不再为每个字段 `normalize()` 出字符串 | 检索 32 → 10 ms（500 味 4.3 → 1.27） |
| 归一化快路径 | `remove_redundant` 无前缀无空白时直接返回 | 索引重建、检索、指纹全线受益 |
| WAL 收敛 | WAL > 16 MB 时 `wal_checkpoint(TRUNCATE)`（有测试证明会截断） | 一次大导入后不再长期占双倍磁盘 |

等价性有测试兜底（`crates/mneme-store/tests/persist.rs`）：增量索引 == 全量重建、
改一条只重算它自己的卡、重开缓存后卡 id 集合完全一致、镜像重复打开不重复写。

## 6. 语料敏感度（我第一版语料被自己证伪了）

第一版语料只用 12 个固定词循环填充，我担心 posting 被放大几十倍会虚高卡片成本，于是改成
720 词表（真实教材的量级：平均每个功效词 2~6 味药在用）重测。结果：

| 语料 | 2000 味冷启动 | 派生 | 500 味单条卡片 | 2000 味单条卡片 |
| --- | --- | --- | --- | --- |
| 12 词循环（posting 平均 166 条） | 3427 ms | 1930 ms | — | — |
| 720 词表（posting 平均 3 条） | 3091–3427 ms | 2466–2592 ms | 154 µs | 850–1162 µs |

**假说被证伪**：把 posting 缩短之后，派生并没有变快，反而略慢（卡片更分散、候选更真实）。
所以瓶颈不是「反查要扫多少条」，而是**每张卡自身的固定开销 + 歧义候选名单**。
这条弯路值得留着：要不是改了语料再测一次，我会去优化一个本来不慢的地方（`reverse` 只要 0.3–1.4 µs）。

另一处需要说明的波动：12 词那把测得「单条编辑稳态 1227 ms」，720 词这把是 233–294 ms。
差异来自那次的 `rounds=5` 且首轮极冷（首次 4205 ms），中位数落在 WAL 尚未稳定的区间。
现在的口径统一为：连做 3 次编辑，取第 2 次作为稳态。

## 7. 桌面壳实测（`crates/mneme-desktop`，13 实体真机库副本）

| 阶段 | 首次启动 | 再次启动 |
| --- | --- | --- |
| 库打开（重放+索引+镜像） | 13.9 ms | 9.5 ms |
| axum 监听（随机端口 + 随机 token，仅 127.0.0.1） | 19.9 ms | 13.6 ms |
| WebView 创建（WebView2 环境初始化） | 826–1679 ms | **714 ms** |
| **页面加载完成（首帧）** | **2219 ms** | **870 ms** |

- 结构：一个进程两条线 —— tokio 线程跑 `mneme_server::serve_on(state, listener)`（新增，
  因为桌面壳要先用 `:0` 拿随机端口再开窗，`serve` 自己 bind 会撞端口，实测 10048）；
  主线程跑 tao 事件循环 + wry。UI 直接复用 server 内嵌的那套网页与 API。
- WebView2 首次启动要建用户数据目录（1.7 s），之后 714 ms——占比已远超 store。
  再往下压的首选是预热：进程起一个隐藏 WebView，或常驻托盘进程。
- 壳启动与库打开是串行的，两者完全独立，可以并行（打开库放 tokio 线程）。

## 8. 复现

```bash
cargo build --release -p mneme-cli
./target/release/mneme.exe bench-startup --entities 500  --rounds 9
./target/release/mneme.exe bench-startup --entities 2000 --rounds 5
# 换领域包量别的形状（字段数与文本长度会变）
./target/release/mneme.exe bench-startup --entities 500 --schema domains/neijing.toml
```

`Store::open_timed` 返回 `OpenTimings { snapshot_load, replay, derive, sqlite_rebuild }`，
桌面端可以把这四个数直接打在启动日志里，用于回归对比。
